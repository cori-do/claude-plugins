# The app folder

The repository is the app (layout v3). Everything the platform needs is under one root; everything generated stays
out of git.

```
my-app/
├── cori.toml                    # app id, name, front, auth roles, llm, connector overrides and dev mocks, webhooks
├── AGENTS.md                    # conventions and commands for the agent (written by `cori init`; editable)
├── README.md
├── .gitignore                   # .cori/  node_modules/  .DS_Store  (dist/ too when the front has a build step)
├── .cori/session                # server url + token for the cli; ignored by git, skipped by deploy (mode 0600)
├── workflows/<id>/
│   ├── workflow.yaml            # id (= folder name), name, description, parameters, connectors, steps (ORDERED), endpoint | schedule, result, budget, redact, tags
│   ├── README.md                # goal, dataflow sketch, verification (prose; optional)
│   ├── types.ts                 # zod schemas shared by the workflow's steps
│   ├── steps/<name>.ts          # one top-level step per file; file name = step `name`
│   └── .cori/                   # context.ts, deno.json — generated by `cori workflow new` / `cori check`; never edit, never commit
├── lib/                         # optional TypeScript shared by workflows (`"../../../lib/x.ts"` from a step, `"../../lib/x.ts"` from types.ts); part of every importing workflow's hash
├── stores/<name>/               # Cori Store: rules.yaml, roles/<role>.yaml, migrations/*.sql, seed/*.sql
├── fixtures/<connector>.json    # dev mocks for `cori run`; llm.json keyed by step name
├── front/                       # Vite + React + Tailwind source (`cori init`); generated client at front/src/lib/cori.ts
└── dist/                        # the built front served by Cori (`npm run build` in front/; committed only for `--front plain`)
```

Rules the compiler enforces:
- `cori.toml` at the root; no `cori/` sub-folder, no `manifest.md`, no `NN_` prefixes (the old layout is neither read nor migrated).
- `workflow.yaml` `id` equals the folder name.
- `steps:` lists every top-level step in execution order. A `steps/x.ts` that is not listed, or a listed name without
  its file, is an error. Nested steps stay in their parent's file and are not listed.
- A step's `name` equals its file stem (`steps/load_ticket.ts` declares `name: "load_ticket"`), snake_case.
- A step may import the workflow's own files (`../types`) and `lib/`; nothing above `cori.toml`; no `node:` imports.

## `cori.toml`

```toml
[app]
id = "support-desk"                 # the app id on the server (= folder name by default)
name = "Support Desk"

[front]
root = "dist"
allow = { roles = ["support_agent", "support_lead", "it_admin"] }

[auth]                              # users sign in with the platform's issuer; the app gets its own OIDC client from it
roles = { support_agent = "group:support-agents", support_lead = "group:support-leads" }   # the app's roles (keys); values note the IdP group
principal_claims = ["email", "department"]   # copied into ctx.user; nothing else of the token reaches a run

[parallel]
max_concurrency = 8                 # default for every workflow; workflow.yaml `parallel:` overrides

# Connectors are declared at org level. A block here means the app uses one and may mock it. In a hosted run the org
# registry's declaration is the connector (this block keeps its dev mock and worker pin); a connector only this file
# declares gets no credential: `secret`, `audience` and `auth_env` come from the registry (`cori deploy` warns).
[connectors.helpdesk]
kind = "mcp"                        # mcp | http | store | activity | cli
ref = "helpdesk-mcp"                # the org connector's name in the registry
audience = "helpdesk-mcp"           # token exchange audience (auth = principal connectors)
command = ["deno", "run", "fixtures/helpdesk_mcp.ts"]   # builder-local stdio server (relative to the app root); a real one has url = "https://…/mcp"
[connectors.helpdesk.dev]
mock = "fixtures/helpdesk.json"     # what `cori run` answers with

[connectors.slack]
kind = "http"
ref = "slack-bot"
base_url = "https://slack.com"
auth_env = "SLACK_BOT_TOKEN"        # `cori run`: the credential from your environment; hosted: the registry's (auth = service)
[connectors.slack.dev]
mock = "fixtures/slack.json"

[connectors.tickets]
kind = "store"
ref = "support_tickets"             # stores/support_tickets/
[connectors.tickets.dev]
mock = "fixtures/tickets.json"

[connectors.billing]
kind = "activity"
ref = "billing-activities"
task_queue = "cori.acme.native.billing"
[connectors.billing.dev]
mock = "fixtures/billing.json"

[connectors.gws]
kind = "cli"
ref = "gws"
worker = "sandbox"                  # cli steps run in a sandbox (or on a named pool)
[connectors.gws.dev]
mock = { argv0 = "gws", stdout = "{\"updates\":{\"updatedRows\":2}}" }

[llm]
provider = "mock"                   # openai | vllm | mock; api_key_env = "OPENAI_API_KEY", base_url for a gateway
mock = "fixtures/llm.json"
tiers = { small = "gpt-5-mini", medium = "gpt-5-mini", large = "gpt-5" }
[llm.dev]
provider = "mock"                   # what `cori run` and `cori up` use whatever [llm].provider says
mock = "fixtures/llm.json"

[[webhooks]]                        # optional: notify the app's backend or Slack
url = "https://hooks.example/cori"
events = ["run.completed", "run.failed", "approval.pending"]
secret_env = "CORI_WEBHOOK_SECRET"  # HMAC signature
format = "json"                     # json | slack
```

Connector field reference (`ConnectorConfig`): `kind`, `ref`, `audience`, `worker`, `base_url`, `auth_env`,
`secret`, `task_queue`, `url`, `command`, `dev.mock`. Only `kind` and `ref` are common to every kind; the rest belongs
to one transport. `cori store new <name>` appends the store block for you.

`[llm]` is optional on a server. Without a provider of its own, an app's `llm` steps get the org's default model for
their tier (console, LLM), and where the org set none, the server's starter model when it offers one: free, shared,
and limited to a few calls a minute and a day per organization (`BudgetExceeded` once the day's are used). Keep
`[llm.dev]` for `cori run`. Do not send confidential data to the starter model: tell the person to add a provider of
their own for that.

## `workflow.yaml`

```yaml
id: support_ticket_triage                    # = the folder name
name: Triage support ticket
description: Classify an incoming ticket, load the customer's plan, decide priority, ask a lead before escalating, draft a reply.
parameters:
  - { name: ticket_id, type: string, description: Helpdesk ticket id }
  - { name: amount_eur, type: number, min: 1 }
  - { name: laptop, type: boolean, required: false }
  - { name: channel, type: enum, values: [email, chat], default: email }
  - { name: ticket_ids, type: list }
connectors: [helpdesk, tickets, slack]       # every connector a step of this workflow names (a listed but unused one is a warning, an unlisted used one an error)
steps: [load_ticket, classify, lookup_customer, decide_priority, escalate_gate, notify, draft_reply]   # REQUIRED, ordered
endpoint:                                    # or schedule: (below); a workflow has one trigger
  auth: sso
  allow: { roles: [support_agent, support_lead] }
  mode: sync                                 # sync: 200 with the result within 30 s, else 202 + run id; async: always 202
  idempotency: parameters                    # parameters | header | none (unset: none without writes, parameters with writes)
  rate_limit: 30/min/principal               # <count>/<s|min|h|d>, per caller with /principal
  timeout: 30s                               # optional; durations are <whole number><ms|s|m|h|d>: 30s, 5m, 4h, 3d
result:
  headline: "Ticket {{ params.ticket_id }} → {{ steps.classify.category }} ({{ steps.decide_priority.priority }})"
  fields:
    - { label: Category, path: steps.classify.category }
    - { label: Escalated, path: steps.approve_escalation.escalated, optional: true }   # a nested step that may not run
  sections:
    - { label: Draft reply, path: steps.draft_reply.reply_draft, display: text }      # display: text | json
budget: { llm_eur_per_run: 0.02, max_duration: 5m }
parallel: { max_concurrency: 8 }
ordering: writes_by_declared_order           # default; or dataflow_only
redact: [steps.load_ticket.ticket.body]      # never stored, never in captured LLM calls
tags: [support]
```

Scheduled workflow (no endpoint):

```yaml
parameters: []
schedule: "0 7 * * 1-5"
schedule_tz: Europe/Paris
schedule_as: { client_id: schedule-support-digest }   # the service account the run acts as; its roles decide what connectors and stores allow
```

Field notes:
- `parameters[].type`: `string | number | boolean | enum | list | object`; `required: false` (or a trailing `?` in
  `--params`) makes it optional; `values` for `enum`; `default`; `min`/`max` for numbers; `description` becomes the
  form label in the generated client and the console.
- `endpoint: true` expands to `auth: sso`, `mode: async`, `allow: { roles: <app roles> }`, and the derived idempotency (`none` without writes, `parameters` with writes).
- `result` paths are dotted only: `params.<name>` or `steps.<step>.<field>[.<field>…]`. No filters, no `[0]`, no
  `.length` (compute those in a `code` step). A missing value renders as an empty string. `cori check` rejects unknown
  steps and parameters and warns when a field is not in the step's output schema.
- `idempotency: parameters`: same caller + same parameters within 24 h replays the earlier run (writes started from a
  form). `header`: the client sends `Idempotency-Key` (the generated client's `start(input, { idempotencyKey })`), one
  key per form instance; the same key with different parameters is rejected (422). `none`: reads, and workflows that
  must run on every call, like a toggle (open → done → open repeats the first call). Unset, it is `none` for a
  workflow without writes and `parameters` with writes, and `cori check` warns on the latter. Previews honor the mode too, keyed per version. Only a running (202) or succeeded (200) run
  is replayed, with `idempotent_replay: true`; after a failed run the same request runs again.
- `redact` paths and `pii` store columns: a step that exposes a `pii` column without a `redact:` entry is a `check` warning.
- Only the promoted version schedules; preview runs deliver no webhook.

## Fixtures

`cori run` answers every connector from `fixtures/` unless told otherwise. One file per connector, named by the
connector's `[connectors.<x>.dev] mock` path; `fixtures/llm.json` for `llm` steps.

```jsonc
// fixtures/helpdesk.json (mcp): tool name → result (what `parse` receives, or the output when there is no parse)
{ "tools": { "getTicket": { "id": "T-1042", "subject": "…", "body": "…", "customer_id": "C-77" }, "addReply": { "reply_id": "R-9001" } } }

// fixtures/tickets.json (store): tools by name; query rows by STEP name (`"*"` for every query step)
{ "tools": { "getCustomer": { "plan": "pro", "arr_eur": 4800 }, "createRefundRequest": { "id": "RR-31" } },
  "query": { "stale_tickets": [ { "ticket_number": "T-1001", "subject": "…", "department": "IT", "created_at": "2026-09-01T08:00:00Z" } ] } }

// fixtures/slack.json (http): "<METHOD> <path>" → { status, json | text }
{ "http": { "POST /api/chat.postMessage": { "status": 200, "json": { "ok": true, "ts": "1726000000.000100" } } } }

// fixtures/billing.json (activity): activity name → result
{ "activities": { "IssueRefund": { "refund_id": "RF-2026-0091" } } }

// cli: inline in cori.toml — mock = { argv0 = "gws", stdout = "…" }

// fixtures/llm.json: step name → output (must satisfy the step's zod schema); `{{item.x}}` inside a map
{ "classify": { "category": "billing", "confidence": 0.93 },
  "summarise_department": { "department": "{{item.department}}", "summary": "…" } }
```

Store fixtures do not run SQL: a `query` fixture is returned as is. Key it by step so each query gets its own rows,
and run against the real store (`cori up`, or `--store-database-url`) before deploying. `cori run --record --no-mock
<connector>` calls the live connector once and writes the request/response pairs as its fixture (redacted by the
connector's rules).

## Sessions and credentials

Resolution order for every server-touching command: `--server`/`--token` flags → `CORI_SERVER`/`CORI_TOKEN` →
`<app>/.cori/session` → `~/.cori/config.toml` (admin commands run outside an app) → a local `cori up` at
`http://127.0.0.1:8080` with your dev identity `dev:<you>:it_admin` (never used by promote, approve, rollback, protect
or deletions). Inside an app folder the session file is the single source of both the server and the identity. A
stored token (the session file, `~/.cori/config.toml`) only goes to the server it was issued for: `--server` naming
another server gets none of them, and the dev identity only goes to a server on this machine.

```toml
# .cori/session (TOML, 0600) — written by `cori login`, `cori init`, `cori pull`, or from the MCP `login` tool
server     = "https://cori.acme"
app        = "my-app"
kind       = "agent"                  # agent | human
token      = "eyJ…"
expires_at = "2026-09-16T11:04:00Z"
scopes     = ["registry:read", "versions:publish", "runs:preview", "stores:read"]
```

- An **agent** session (from the MCP `login` tool): one app, 1 h by default (4 h max). It checks and runs locally,
  deploys and pulls versions of its app and reads their sandbox stores (`--version <hash>`); it cannot promote,
  approve, rollback or administer, reach live data or live runs, or touch another app, whatever its human may do. It
  does not refresh: when the cli says the session expired, call `login` again.
- A **human** session (`cori login <url>` in the folder: browser + PKCE, `--device` without a browser, `--token` as
  given for dev or CI): refreshes itself; carries approve and promote.
- Dev mode (`cori up`): tokens look like `dev:<sub>:<role,role>`; with no session every command uses `dev:<you>:it_admin`.
- `.cori/` is ignored by git and skipped by `deploy`; the token never enters a commit or a bundle. Never print it.
- Credential files (`.env`, `.env.*`, `.npmrc`, `.netrc`, `*.pem`, `*.key`, `*.p12`, `*.pfx`) never enter a bundle:
  `cori deploy` leaves them out and names them, and the server refuses a bundle that carries one.

## Git

`cori init` runs `git init` and a first commit (`--no-git` to skip). `cori deploy` records the commit, branch and
dirty flag on the version; `--require-clean` refuses a dirty tree. Cori keeps no remote and speaks no git protocol:
the forge owns history, `cori pull <app>` restores the folder from the version Cori stores. Commit before `deploy`
so the version points at a real commit.
