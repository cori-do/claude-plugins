# The front

Cori serves `dist/` at `/apps/<app>/` (the promoted version) and `/apps/<app>/@<hash>/` (a deployed version's
preview, whose calls go to that version's workflows and sandbox stores). The front authenticates with the org SSO in
production and with `dev:<sub>:<roles>` under `cori up`; `[front].allow.roles` in `cori.toml` says who may load it.

## The default: Vite + React + TypeScript + Tailwind in `front/`

Any front a person will use is a real app: `front/` built with Vite into `dist/`, React 19, TypeScript strict,
Tailwind v4 and the generated client. `cori init` writes it for a new app (`--front react`, the default; add it to a
template with `cori init <dir> --template support-desk --front react`; `team-requests` ships it with its screens, built).
Build the screens from the first pass; do not
ship the starting Home view or a single `index.html` and wait to be asked for a better one. The plain-`fetch` page
below is only for a smoke test or when the user explicitly wants no build step (`--front plain`).

### Files (as `cori init` writes them)

```
front/
├── package.json        # scripts: gen, dev, typecheck, build ("npm run gen && tsc --noEmit && vite build")
├── vite.config.ts      # base "./", react + tailwind plugins, @cori-do/client alias, outDir ../dist, dev proxy
├── tsconfig.json       # strict, moduleResolution bundler, allowImportingTsExtensions, paths for @cori-do/client
├── index.html          # <div id="root">, <script type="module" src="/src/main.tsx">, title, viewport, favicon
├── vendor/cori-client/ # @cori-do/client (index.ts + react.ts), carried by the cli: not on npm
└── src/
    ├── main.tsx        # bootstrap() then createRoot
    ├── styles.css      # @import "tailwindcss"; @theme { font, brand color scale }
    ├── App.tsx         # shell: header (name, preview badge, nav, user + roles), hash routing, a state for no screen
    ├── lib/cori.ts     # generated by `cori gen client` — never edit
    ├── lib/api.ts      # bootstrap (config, dev identity), must() / RunFailed, newIdempotencyKey, formatValue
    ├── lib/app.ts      # APP_NAME
    ├── components/     # ui.tsx (Button, Card, Badge, Field, Input, Select, Textarea, Spinner, EmptyState, ErrorBanner), RunResult.tsx
    └── views/          # index.tsx: the VIEWS registry; Home.tsx: the starting screen, replace it
```

```bash
cd front && npm install && npm run dev        # http://localhost:5173 against `cori up` (the app promoted locally)
npm run build                                 # before `cori deploy`
```

A new screen: a file in `src/views/`, an entry in `VIEWS` (`src/views/index.tsx`: `{ id, label, icon, component, roles? }`), the workflow
object from `lib/cori.ts`, the kit's `Field` + `Input` for its parameters and `RunResult` for its run. Add
`@tanstack/react-query` when the app lists, filters and refetches data (several views reading the same runs).

For an app created before this (no `front/package.json`): `cori init /tmp/scratch --app <id> --no-register --no-git`
and copy its `front/`, then add `dist/` to `.gitignore` and `git rm -r --cached dist`.

### `vite.config.ts` (what init writes, for reference)

```ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import tailwindcss from "@tailwindcss/vite";
import { fileURLToPath } from "node:url";

const APP = "my-app";
const server = process.env.CORI_SERVER ?? "http://127.0.0.1:8080";
const vendor = (f: string) => fileURLToPath(new URL(`./vendor/cori-client/${f}`, import.meta.url));

export default defineConfig({
  base: "./",                                   // the same build serves /apps/<app>/ and every /apps/<app>/@<hash>/ preview
  plugins: [react(), tailwindcss()],
  resolve: { alias: [
    { find: /^@cori-do\/client\/react$/, replacement: vendor("react.ts") },
    { find: /^@cori-do\/client$/, replacement: vendor("index.ts") },
  ] },
  build: { outDir: "../dist", emptyOutDir: true },
  server: { proxy: {                            // `npm run dev` against `cori up`
    "/__cori": { target: server, changeOrigin: true, rewrite: (p) => `/apps/${APP}${p}` },
    "/v1": server,
  } },
});
```

`tsconfig.json` mirrors the alias: `"paths": { "@cori-do/client": ["./vendor/cori-client/index.ts"],
"@cori-do/client/react": ["./vendor/cori-client/react.ts"] }`, with `"allowImportingTsExtensions": true`,
`"types": ["vite/client"]` and `"include": ["src", "vendor"]` (the vendored files import `./index.ts`).

### Rules that bite

- **`base: "./"` and hash routing.** The server falls back to `index.html` for unknown paths, so a
  `BrowserRouter` path like `/apps/x/tickets/42` loads `./assets/…` relative to `tickets/` and gets HTML back. Route
  on `location.hash` (`#/tickets/42`, a `hashchange` listener, or `createHashRouter`); never use absolute `/assets`.
- **`dist/` is build output** (ignored by git): run `npm run build` in `front/` before every `cori deploy`, since the
  bundle takes `dist/` from the working tree. `cori deploy` warns when `dist/` is missing or older than `front/` or
  `workflows/`.
- **The client follows the workflows.** `npm run build` regenerates `src/lib/cori.ts` first, so `tsc` catches every
  call site a parameter, `result` or endpoint change broke; it needs `cori` on the PATH and a clean `cori check`.
- **A failed run resolves, it does not throw.** Wrap `run()` so `status !== "succeeded"` becomes an error the UI shows
  (`r.errorDetail?.message ?? r.error`); `CoriError` is only for HTTP 4xx/5xx.
- **Dev personas live in cori.toml**, not in the front: `[[dev.personas]] sub, roles, name?, title?`, one per kind of
  user, with subs that match the stores' seed (the first is the default identity). The dev widget offers them; an
  in-app switcher, if any, reads `devPersonas(cfg)` and calls `setDevIdentity`, nothing more. The identity is kept per
  app (`cori.tok.<app>`) and previews accept it under `cori up`: no role checks, no `approver` padding in the front.
  Data a view loads should refetch on `onDevIdentityChange`.
- Fonts from Google Fonts in `index.html` are fine; do not load scripts or CSS frameworks from other CDNs.

### What a finished front has

- **Every workflow a role can start is reachable** with a form built from its parameters: labels from the parameter
  descriptions, enums as selects, optional fields marked, client-side validation matching the zod schema.
- **Four states on every call:** idle, pending (disabled button + spinner; for `async` runs, `useRun` with the live
  step list), success (the run's `result.headline` prominent, `fields` as a readable summary, never raw JSON), and
  error (the message and the failing step, with a retry). Plus an empty state for every list.
- **Roles shape the UI:** `useUser` in the header; `<Protected roles={…}>` around views a role cannot use rather than
  buttons that 403.
- **Human gates have a home:** when any workflow has a `human` step, an approvals inbox (`useApprovals`) for the
  routed role, showing what is being decided and why, with the decision form.
- **Double submits are safe:** one `idempotencyKey` per form instance on endpoints with `idempotency: header`.
- **Looks like a product:** a consistent layout (header, nav, max-width content), a spacing and type scale, cards and
  tables with aligned numbers, status badges with color and text, `lucide-react` icons, responsive down to phone
  width, visible focus states and labelled inputs. No lorem ipsum, no default Vite page, no unstyled HTML controls.
- **Verified in a browser:** open the preview url (or `npm run dev` against `cori up`), run each workflow as each
  role, and look at it before reporting.

## Without a bundler: plain `fetch` in `dist/index.html`

For a smoke test or a user who asked for no build step. The template's `dist/index.html` is the reference. It reads
`__cori/config.json` next to the app, then posts to the run endpoint:

```html
<script type="module">
  const base = (location.pathname.match(/^\/apps\/[^/]+\/(@[^/]+\/)?/) || ["/"])[0];   // hosted under /apps/<app>/ or at a domain root
  const cfg = await (await fetch(`${base}__cori/config.json`)).json();       // { app, baseUrl, auth, version, preview, dev }
  const token = () => localStorage.getItem(`cori.tok.${cfg.app}`) || "dev:alice:support_agent";   // the dev widget's identity for this app; production: the SSO JWT
  const wf = cfg.preview && cfg.version
    ? `${cfg.baseUrl}/v1/apps/${cfg.app}/versions/${cfg.version}/wf/support_ticket_triage/runs`   // a preview runs its own version
    : `${cfg.baseUrl}/v1/apps/${cfg.app}/wf/support_ticket_triage/runs`;
  const r = await fetch(wf, { method: "POST", headers: { "content-type": "application/json", authorization: `Bearer ${token()}` },
                              body: JSON.stringify({ ticket_id: "T-1042" }) });
  const j = await r.json();   // 200: finished (succeeded or failed) · 202: { run_id, status: "running", poll } · 4xx: { error }
</script>
```

Under `cori up` the server injects a dev widget (bottom right) to pick an identity; it writes `cori.tok.<app>`. `cfg.dev`
lists the app's roles and personas, workflows with their endpoints, and which connectors are mocked.

## With a bundler: the generated client

```
cori gen client --dir . --out front/src/lib/cori.ts      # from the local folder; or --app <id>: the promoted version, from the server (its builders)
```
emits one typed function per workflow (derived from the same zod schemas as the runtime and from `result`), over
`@cori-do/client` (vendored by `cori init` in `front/vendor/cori-client/`). `npm run build` regenerates it first (the
`gen` script), so run the build after every workflow change.

```tsx
import { cori, supportTicketTriage, refundRequest } from "./lib/cori";
import { useRun, useApprovals, useUser, Protected } from "@cori-do/client/react";

const user = useUser(cori);                                       // { sub, roles, email, loading } as the server sees the caller
const triage = await supportTicketTriage.run({ ticket_id });      // waits: RunView { runId, status, error, errorDetail, result, outputs, steps }
const { runId } = await refundRequest.start({ ticket_id, invoice_id, amount_eur }, { idempotencyKey });   // async: idempotency: header
const refund = useRun(cori, runId);                               // { status, steps (so far, while running), result, pendingApproval: { step, to, since } while it waits for a person }
const { approvals, decide } = useApprovals(cori);                 // items routed to the caller's roles, across workflows
<Protected client={cori} roles={["support_lead"]}><ApprovalsInbox /></Protected>
```

`createCoriClient({ baseUrl, app, getToken })` is the low-level client; `CoriError` carries the HTTP status of a 4xx/5xx.
A failed run is not a `CoriError`: `run()` resolves with `status: "failed"`, check it. The client maps the wire's
snake_case to camelCase (`run_id` → `runId`, `error_detail` → `errorDetail`, `started_at` → `startedAt`). One
`idempotencyKey` per form instance (`useState(() => crypto.randomUUID())`) makes a double submit replay the first run.

## The app API (what the client wraps)

These paths are the contract between a built app and the server. Every front carries its own copy of
`@cori-do/client`, so a deployed front keeps calling them after the server is upgraded: they change by addition only,
never by renaming or removal. Call them through the generated client; a hand-written `fetch` uses the same paths.

```
GET  /v1/auth/config                                     sign-in mode, issuer, client ids (read before signing in)
GET  /v1/me                                              the caller as the server sees it
GET  /v1/apps/{app}                                      the app (a member's view: name, roles, workflows)
GET  /v1/apps/{app}/me                                   the caller inside the app: app roles and platform roles
POST /v1/apps/{app}/wf/{workflow}/runs                   start the promoted version's workflow (body: the parameters)
POST /v1/apps/{app}/versions/{hash}/wf/{workflow}/runs   the same on a deployed version (preview, sandbox stores)
GET  /v1/apps/{app}/runs                                 the latest 100 runs (your own; builders and operators see all)
GET  /v1/apps/{app}/runs/{run_id}                        status, params, error, error_detail, result, outputs, steps
GET  /v1/apps/{app}/runs/{run_id}/events                 recorded run events (JSON list)
GET  /v1/apps/{app}/runs/{run_id}/stream                 progress as server-sent events
POST /v1/apps/{app}/runs/{run_id}/decisions/{step}       answer a `human` step (body: the decision value)
GET  /v1/apps/{app}/approvals                            pending approvals for the caller's roles
POST /v1/apps/{app}/approvals/{id}                       decide one (body: the decision value)
GET  /apps/{app}/__cori/config.json                      the front's config (app, baseUrl, auth, version, preview, dev)
GET  /apps/{app}/callback                                the sign-in redirect back into the front
GET  /apps/{app}/__cori/dev-widget.js                    the dev widget, under `cori up` only
```
A deployed version's preview serves the front and its `__cori/` files under `/apps/{app}/@{hash}/`.
`GET /v1/apps/{app}/client.ts` is for build time, not for the running front: `cori gen client --app <id>` fetches it
with a builder's session.

Starting a run answers:
- **200** when a `sync` run finished in time: `{ run_id, status: "succeeded" | "failed", error, error_detail, result,
  outputs, steps }`. **A failed run is still HTTP 200**: check `status`. `result` is `{ headline, fields, sections,
  values }` (null when the run failed), `outputs` maps each step name to its output, `steps` is the trace
  (`{ name, kind, status, ms, cost_eur, notes, error }` per step).
- **202** for `async` endpoints and for sync runs past their timeout: `{ run_id, status: "running", poll }`; `GET poll`
  until `status` is not `running`.
- **400** invalid parameters (missing, wrong type, value not in an enum), **401/403** caller not allowed, **422** an
  `Idempotency-Key` reused with different parameters, **429** rate limit (`retry_after_secs`); body `{ error }`.
- An idempotent replay carries `idempotent_replay: true` (and the header `x-cori-idempotent-replay`).

On failure `error` is the message to show (e.g. `Todo not found`) and `error_detail` says where it came from:
`{ step, type, message }`, `type` being `StepFailedError` (a step threw), `SchemaValidationError`, `Timeout`,
`BudgetExceeded` (no `step`)… Runs recorded before `error_detail` existed have none.

All with `Authorization: Bearer <JWT>` (`dev:<sub>:<roles>` under `cori up`). Webhooks out (`run.completed`,
`run.failed`, `approval.pending`, HMAC-signed) are configured in `cori.toml` `[[webhooks]]`; preview runs send none.

## Build step or not

- With `front/package.json` and a `build` script (the default above): build locally into `dist/` before `cori deploy`
  and keep `dist/` in `.gitignore`; the bundle includes it when present. Server-side builds are not part of this loop.
- No build: commit `dist/` (the template does).
